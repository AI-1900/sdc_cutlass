**一、为什么一个 GEMM 要拆成这么多部件？**

标准 GEMM 可以写成：

\[
D=\alpha AB+\beta C
\]

其中 \(A\) 是 \(M\times K\)，\(B\) 是 \(K\times N\)，输出是 \(M\times N\)。

最直接的实现，是每个线程计算一个输出元素：

\[
D_{m,n}=\alpha\sum_{k=0}^{K-1}A_{m,k}B_{k,n}+\beta C_{m,n}
\]

这个表达式说明了计算结果，却没有解决 GPU 高性能实现中的关键问题：

| 必须决定的问题 | 对性能的影响 |
|---|---|
| 一个线程块负责多大的输出区域？ | 决定工作量、数据复用和资源占用 |
| A、B 怎样搬入共享内存？ | 决定访存合并、带宽利用和搬运开销 |
| 哪些线程负责哪些元素？ | 决定数据能否匹配 Copy/MMA 指令 |
| 用哪种矩阵乘加指令？ | 决定计算吞吐与操作数组织 |
| 怎样让加载与计算重叠？ | 决定能否隐藏数据搬运延迟 |
| 累加结果如何缩放、转换、融合和存储？ | 决定输出阶段开销与额外访存 |

CUTLASS 将这些问题分配给不同层次，让一个部件可以在约定的接口和约束下与其他部件组合。它保留了分块 GEMM 的高性能结构，同时允许针对类型、布局、指令和调度进行特化。[NVIDIA GEMM 分块结构](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/efficient_gemm.md)

**二、计算分块：先把整个矩阵变成一个个能复用数据的小任务**

假设选定一个教学配置：

\[
B_M=128,\quad B_N=128,\quad B_K=64
\]

一个工作 tile 负责输出中的 \(128\times128\) 区域。它沿着 K 维前进，每次取：

- A 中的一个 \(128\times64\) 分块；
- B 中的一个 \(64\times128\) 分块；
- 将二者的乘积累加到同一个 \(128\times128\) 输出 tile。

```text
输出 tile 的累加器清零
        │
        ├─ K 分块 0：Acc += A₀ × B₀
        ├─ K 分块 1：Acc += A₁ × B₁
        ├─ K 分块 2：Acc += A₂ × B₂
        └─ ……
        │
        ▼
Epilogue：D_tile = α·Acc + β·C_tile
```

这里的关键是**复用**：同一份 A 分块参与多个输出列的计算，同一份 B 分块参与多个输出行的计算。共享内存和局部累加存储让这些数据能在片上重复使用。

这个 \(128\times128\times64\) 分块还会进一步拆成适合具体矩阵指令的操作。高层 tile 大小与单条 MMA 指令的形状通常不同。

tile 也并非越大越好。更大的 tile 可能提高复用，同时增加共享内存、累加存储和寄存器需求，影响并发度与边界利用率。实际选择需要匹配 GPU 和问题形状。

**三、架构树：每一层负责什么？**

CUTLASS 3.x 的五层概念架构是：

```text
Device
└── Kernel
    ├── CollectiveMainloop
    │   ├── TiledCopy
    │   │   └── Copy Atom / Traits
    │   ├── TiledMMA
    │   │   └── MMA Atom / Traits
    │   └── Pipeline / 同步协议
    │
    ├── CollectiveEpilogue
    │   └── 输出变换、可选融合、存储
    │
    └── Tile Scheduler / 资源与线程角色组织
```

| 层次 | 核心问题 | 典型职责 |
|---|---|---|
| **Device** | 应用怎样调用这个 GEMM？ | 参数检查、workspace、参数转换和启动 |
| **Kernel** | 整个 GPU kernel 怎样组织？ | 工作 tile 调度、线程角色、共享资源、Collective 生命周期 |
| **Collective** | 一组参与线程怎样完成协作？ | K 维主循环、搬运和计算的编排、同步；或输出处理 |
| **Tiled MMA / Copy** | 如何把基本操作铺到更大的 tile？ | 线程切片、元素分配、基本操作的空间重复 |
| **Atom / Traits** | 一次基本操作要求什么？ | 指令形状、参与线程、操作数布局、fragment 和接口约定 |

Atom 再通过架构封装连接到 PTX 指令及相关 descriptor、barrier、TMEM 等机制。

这里有三个容易混淆的地方：

- **Collective** 表达协作与执行编排，不能固定理解成某一种 warp 或线程块。
- **Tiled** 表达基本操作在空间上的铺开，不能固定等同于 warp 层。
- **Atom** 表达基本操作单元，与 `atomicAdd` 中的内存原子性是不同概念。

这种按职责划分的层次，使空间映射、时间协作和主机调用可以分别组织。[NVIDIA CUTLASS 3.0 设计](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/cutlass_3x_design.html)

**四、CuTe：怎样把“矩阵”连接到“线程和指令”？**

CuTe 最重要的作用，是把复杂的索引关系变成可以组合、变换和检查的对象。

可以按三个步骤理解：

```text
Layout：坐标怎样变成索引？
    ↓
Tensor：这个索引对应哪份数据？
    ↓
线程/值映射：每个参与线程负责哪些元素？
```

**1. Layout：一个坐标到索引的映射**

对于普通二维布局，可以先理解为：

\[
L(m,n)=m\,s_m+n\,s_n
\]

例如一个行主序 \(4\times4\) 矩阵：

```cpp
auto layout = cute::make_layout(
    cute::make_shape(cute::Int<4>{}, cute::Int<4>{}),
    cute::make_stride(cute::Int<4>{}, cute::Int<1>{})
);
```

对应：

\[
L(m,n)=4m+n
\]

所以：

```text
坐标 (0,0) → 偏移 0
坐标 (0,3) → 偏移 3
坐标 (1,0) → 偏移 4
坐标 (2,3) → 偏移 11
```

这里得到的是**元素索引或偏移**。结合存储引擎、元素类型和基地址之后，才能形成具体的数据访问。

CuTe Layout 还支持嵌套 Shape/Stride，能够表达线程、warp、指令和子 tile 等层次。共享内存中还可能使用 swizzle 等组合布局，因此不能把所有布局都简化成普通二维行列步长。

本地实现可从 [layout.hpp:167](E:/000wsp/01repo/08sutlass/cutlass/include/cute/layout.hpp:167) 开始阅读。

**2. Tensor：将数据引擎与 Layout 结合**

从使用者的角度，可以把 Tensor 理解为：

\[
\text{Tensor}=\text{数据引擎}+\text{Layout}
\]

例如，以全局内存指针构造一个 tensor 视图后，访问 `tensor(m,n)` 时，Layout 决定访问哪个位置。

**构造视图、切片或改变索引组织，通常不意味着已经搬运数据。** 真正的数据搬运由 `copy` 等操作完成；矩阵计算由 `gemm` 等操作分派到具体实现。

**3. 线程—值映射：一个线程可以负责多个元素**

GPU 指令的参与方式往往比“一个线程一个元素”复杂。需要描述：

\[
(\text{thread},\text{value})\rightarrow(m,n)
\]

这里的 `value` 表示某个线程所负责的第几个逻辑元素。

交互图中的教学例子使用四个线程，每线程四个元素：

```text
          n=0    n=1    n=2    n=3
m=0       T0     T2     T0     T2
m=1       T1     T3     T1     T3
m=2       T0     T2     T0     T2
m=3       T1     T3     T1     T3
```

映射规则为：

\[
m=(t\bmod2)+2(v\bmod2)
\]

\[
n=\lfloor t/2\rfloor+2\lfloor v/2\rfloor
\]

例如线程 T3 的第 3 个值：

```text
(t=3, v=3)
    → 矩阵坐标 (3,3)
    → 行主序偏移 15
```

这就把两个问题连接起来了：

```text
谁负责这个元素？                 这个元素在哪里？
(thread, value) → 逻辑坐标 → 数据布局 → 存储位置
```

真实 Copy/MMA 操作的线程—值映射必须满足目标指令的约定，不能任意设计。CuTe 的 Atom Traits、Tiled 操作和布局代数共同描述、组合这些关系。[NVIDIA CuTe Tensor 与线程划分说明](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/cute/03_tensor.md)

**五、从一个 Atom 到整个 tile，CuTe 如何组合映射？**

这里可以抓住四种操作：

| 操作或对象 | 直观含义 |
|---|---|
| `local_tile` | 从大 tensor 中取出当前工作 tile 的视图 |
| `composition` | 将索引变换组合起来，概念上是 \(A(B(x))\) |
| divide / tiling | 将一个域组织成“tile 内部位置”和“tile 编号”等模式 |
| `get_slice` / `partition_*` | 给出某个参与线程在相应操作中的数据视图 |

一个简化的过程是：

```cpp
// 示意：省略了真实配置与同步代码。
auto tile = local_tile(global_tensor, tile_shape, tile_coord);

auto thr_mma = tiled_mma.get_slice(threadIdx.x);
auto thread_view = thr_mma.partition_C(tile);
```

这个过程表达：

1. 先决定当前工作 tile；
2. 再根据 TiledMMA 的映射找到当前线程；
3. 得到该线程在输出 tile 中所负责的部分。

Copy 与 MMA 对数据的组织要求可能不同，因此还需要兼容的 copy 布局、fragment 布局和重排方式。**TiledMMA 的作用，是在满足基本 MMA 操作约定的前提下，将其铺到更大的计算域。**

**六、空间映射确定以后，怎样组织执行时间？**

CuTe 的映射解决了数据分工，但高性能 GEMM 还必须处理加载、计算和缓冲区复用的先后关系。

一个概念性的分块循环是：

```text
取得可写缓冲区
    ↓
将 A、B 的当前 K 分块载入共享内存
    ↓
等待数据就绪
    ↓
执行 MMA，累加当前分块
    ↓
按照架构协议确认消费完成
    ↓
释放缓冲区，供后续加载复用
```

为了重叠搬运与计算，可以采用多阶段流水线：

```text
时间 →       t0          t1          t2          t3

加载         tile 0      tile 1      tile 2       …
计算         等待        tile 0      tile 1      tile 2
```

它通常通过多个共享内存缓冲槽位，让生产者准备后续数据，同时消费者计算当前数据。

需要区分两件事：

- **数据已经可以读取；**
- **使用这些数据的异步计算已经完成，可以安全覆盖缓冲区。**

二者可能依赖不同的同步机制。Hopper、Blackwell 的异步执行协议不能直接套用普通同步函数的直觉；具体实现由 Collective、Pipeline 和架构操作共同承担。

**七、这些部件在 C++ 中怎样真正组装？**

本地示例 49 展示了清晰的组合顺序：

```cpp
// 结构示意，省略完整模板参数。
using Epilogue =
    typename EpilogueBuilder<...>::CollectiveOp;

using Mainloop =
    typename MainloopBuilder<
        ...,
        StageCountAutoCarveout<
            sizeof(typename Epilogue::SharedStorage)
        >,
        MainloopSchedule
    >::CollectiveOp;

using Kernel =
    cutlass::gemm::kernel::GemmUniversal<
        cute::Shape<int, int, int, int>,
        Mainloop,
        Epilogue,
        TileScheduler
    >;

using Gemm =
    cutlass::gemm::device::GemmUniversalAdapter<Kernel>;
```

可以理解成：

```text
选定 Epilogue
    ↓ 得到其共享内存需求
构建 Mainloop
    ↓ 结合资源预算、架构与策略选择实现
组合 Kernel
    ↓ 组织调度、资源与生命周期
包装 Device Adapter
    ↓
供主机程序调用
```

示例先定义 Epilogue，是为了让 Mainloop 的自动 stage 选择考虑其共享内存占用。最终可用预算仍应以具体 Kernel 的资源组织为准。

可直接阅读 [49_collective_builder.cu:307](E:/000wsp/01repo/08sutlass/cutlass/examples/49_hopper_gemm_with_collective_builder/49_collective_builder.cu:307)。

这些部件虽然可组合，仍需满足类型、tile、对齐、存储布局、schedule 和同步协议等兼容约束。Builder 帮助完成其中一部分选择。[NVIDIA GEMM API 说明](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/gemm_api_3x.md)

**八、编译期特化：抽象怎样变成适合 GPU 的代码？**

首先要区分编译期配置与运行时输入：

| 通常在编译期确定 | 通常在运行时传入 |
|---|---|
| 目标架构标签 | 矩阵地址 |
| 元素和累加类型 | M、N、K、batch 数 |
| Layout 类型及静态部分 | 动态 stride 值 |
| Tile、Cluster 形状 | α、β |
| MMA/Copy 操作与流水线策略 | workspace、stream |
| Epilogue 融合操作类型 | 其他运行参数 |

CuTe 允许静态与动态信息混合。例如，Layout 的类型和部分步长可以在编译期确定，另一些步长值在运行时传入。

随后发生四类工作：

**① 模板匹配，选择支持的实现**

Builder 根据架构、类型、布局、对齐、tile 和 schedule 等条件，选择或构造 Mainloop/Epilogue 实现，再选出相应的 Atom、布局与 dispatch policy。

这使最终 kernel 的执行路径具有明确的具体类型。

**② 利用静态信息化简代码**

如果某个映射的 shape、stride 和循环范围已知，编译器就有机会：

- 折叠常量；
- 化简地址计算；
- 消除编译期分支；
- 展开适当的内层循环；
- 内联跨组件调用。

例如，抽象表达：

\[
L(m,n)=4m+n
\]

当某次访问的坐标也已知时，可以进一步确定偏移；当部分坐标动态时，就保留所需的运行时计算。

**③ 架构封装给出具体硬件操作**

MMA/Copy Atom 及 Traits 将上层数据视图连接到具体操作数接口。许多架构操作封装最终发出内联 PTX。

例如，本地 Hopper GMMA 封装中可以看到 `wgmma.mma_async`。[mma_sm90_gmma.hpp:158](E:/000wsp/01repo/08sutlass/cutlass/include/cute/arch/mma_sm90_gmma.hpp:158)

**④ CUDA 工具链生成目标机器码**

```text
C++ / CuTe / CUTLASS 模板
          ↓
具体类型、操作和索引表达式
          ↓
CUDA 编译与优化
          ↓
PTX
          ↓
目标架构机器码 / SASS
          ↓
GPU 执行
```

PTX 是虚拟指令集；最终还涉及目标机器码生成、寄存器分配和指令调度。部署中也可能保留 PTX，由驱动进行 JIT。

**静态抽象为生成直接代码创造条件，但最终性能仍取决于生成结果和运行负载。** 寄存器压力、spill、访存冲突、同步和调度都可能成为瓶颈。

**九、编译好的 kernel 怎样处理一次实际 GEMM？**

主机侧的常见调用流程是：

```text
构造 Arguments
    ↓
查询 workspace 大小，并检查能否实现
    ↓
initialize：转换为底层 Params，准备必要状态
    ↓
run：启动已选定的 kernel
```

对应本地 [gemm_universal_adapter.h:232](E:/000wsp/01repo/08sutlass/cutlass/include/cutlass/gemm/device/gemm_universal_adapter.h:232)。

GPU 端则大致执行：

```text
Kernel 取得工作 tile
    ↓
CollectiveMainloop 沿 K 推进
    ├─ 搬运当前或后续分块
    ├─ 等待所需数据
    ├─ 通过 TiledMMA / Atom 执行乘加
    └─ 按协议释放并复用缓冲区
    ↓
CollectiveEpilogue 处理累加结果
    ↓
缩放、转换、可选融合、存储 D
    ↓
若调度策略允许，继续取得下一个工作 tile
```

同一个编译好的 kernel 可以接收多组运行时尺寸，但其 tile 与指令策略通常固定，输入必须满足实现约束。

`Auto` 主要是按 Builder 规则选择配置；单个 `GemmUniversalAdapter<Kernel>` 也不会自动搜索整个 kernel 库。寻找更优配置需要实例选择、基准测试与调优。

**十、把整个过程落到一个例子上**

假设问题是：

```text
A：4096 × 4096，FP16
B：4096 × 4096，FP16
累加：FP32
输出 tile：128 × 128
K 分块：64
```

在这个没有边界余数的例子里：

- 输出有 \(32\times32=1024\) 个逻辑工作 tile；
- 每个工作 tile 沿 K 处理 \(4096/64=64\) 个分块；
- 每个 K 分块进一步分成具体 MMA 操作。

各部件贯穿同一个任务：

| 阶段 | 在这个例子中做什么 |
|---|---|
| 配置 | 确定架构、FP16 输入、FP32 累加、tile 与策略 |
| Builder | 选择兼容的 Mainloop、Epilogue 和低层操作 |
| CuTe | 描述当前 tile、线程切片、操作数与累加器映射 |
| 编译 | 将这些具体类型和静态映射落实为目标代码 |
| Device | 传入矩阵地址、4096³、stride、α、β 等 |
| Kernel | 将 1024 个逻辑工作 tile 分配给执行单元 |
| Mainloop | 每个工作 tile 完成 64 个 K 分块的累加 |
| Epilogue | 处理结果并存储输出 |

1024 个逻辑工作 tile 与实际启动的线程块数之间的关系，由具体调度策略决定；persistent 调度可能让一个线程块连续处理多个 tile。

**复习时，可以用这五句话检查理解：**

1. **分块**让数据在片上复用，并把问题缩小到可管理的资源范围。
2. **CuTe**把“哪个线程的哪个值”连接到逻辑元素和操作数位置。
3. **Tiled 与 Atom**把大 tile 连接到具体 Copy/MMA 操作。
4. **Collective 与 Kernel**组织搬运、计算、同步、资源和调度。
5. **编译期特化与 CUDA 工具链**把选定的组合落实为目标 GPU 代码。
