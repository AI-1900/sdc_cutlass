# CUTLASS 全局架构梳理：从顶层设计到 GPU 指令的系统性

采用“自顶向下建立架构认知，自底向上验证硬件实现，最后沿完整 GEMM 调用链贯通”的学习路线。

对于 CUTLASS围绕三个核心问题展开：

1. CUTLASS 是如何设计的？ 理解架构分层、抽象边界、组件职责以及组合方式。
2. 一个 GEMM 在 CUTLASS 中如何执行？ 追踪 Host API、Kernel、Collective、CuTe，最终到 PTX 和 GPU 硬件。
3. 如何修改、优化和移植 CUTLASS？ 理解扩展点、调度策略、性能瓶颈，以及新增硬件后端的实现路径。

官方 CUTLASS 3.x GEMM API 明确给出了五级抽象：Device、Kernel、Collective、Tiled MMA/Copy、Atom。CuTe 提供更底层的 Tensor、Layout 等表达能力。当前 CUTLASS 工程还包含 CuTe DSL，因此需要把它与 C++ 模板 API 的学习路径区分开。

阅读时建议始终保留两张图。第一张是**编译期组合图**：配置如何经过 Builder，形成 Collective、Kernel 和 Adapter 类型；第二张是**运行期执行图**：Host 参数如何进入 kernel，数据如何被搬运、计算和写回。五级抽象并不意味着运行时存在五层普通函数依次调用；模板展开、内联和异步操作需要分别追踪。[官方 GEMM API 说明](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/gemm_api_3x.html)

核实过程中，有四点已经写进指南：

- **区分 API 代际与仓库版本。** “3.x GEMM API”指五级接口架构。早期文档中“Builder 仅支持 SM90”的说明不能用于判断当前支持范围；固定提交的 [Builder 入口](https://github.com/NVIDIA/cutlass/blob/78e46228a1bfc5c972e2f9a634223af784cd6949/include/cutlass/gemm/collective/collective_builder.hpp) 已包含 SM100 等架构实现。
- **区分 CuTe C++ 与 CuTe DSL。** 两者共享 Layout、Tensor、Atom 等概念，但 DSL 有自己的 Python 与编译流程，需要单独研究。[官方 DSL 概览](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/overview.html)
- **区分硬件路径。** 指南以具体实例对照 `mma.sync`、`wgmma.mma_async` 和 `tcgen05.mma`，逐项调查操作数、累加器位置、线程参与方式和完成通知。[PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/)
- **拆分“后端移植”的含义。** NVIDIA 架构扩展、跨厂商 GPU 移植和 DSL 编译链迁移各有一条调查路线，并明确了需要重新验证的执行契约。
