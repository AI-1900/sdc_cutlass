## 3. 助手

下面按 Q27–Q32 给出适合 CUTLASS 学习和移植讨论的回答。**你写的“M100”，结合 `tcgen05.mma`，这里按 NVIDIA Blackwell 的 SM100 理解。** 统一使用：

\[
D=\alpha AB+\beta C,\qquad A\in\mathbb R^{M\times K},\quad B\in\mathbb R^{K\times N}
\]

最需要把握的变化是：**传统 GEMM 常按“每个 Warp 持有并计算一块结果”理解；SM100 的 `tcgen05` 路径则要同时考虑线程角色、异步指令和 TMEM 中的数据所有权。**

**Q27｜P0：GEMM 的 Problem、Cluster、CTA、Warp、Instruction Tile 分别如何映射？**

这些 Tile 描述的是不同层级的工作划分，但并非每代架构都严格按照同一棵树执行。

| 层级 | 含义 | 主要负责的工作 |
|---|---|---|
| Problem | 完整的 \((M,N,K)\)，批处理时还可能有 \(L\) 维 | 定义整个 GEMM |
| Cluster | 一组能够协作的 CTA | 组织数据复用、TMA multicast，以及适用时的双 CTA MMA |
| CTA Tile | 一个 CTA，或协作 MMA 中一个 CTA 的工作份额 | 加载局部 A/B，推进 K 循环，生成局部结果 |
| Warp Tile | 传统路径中一个 Warp 的计算区域 | 由多个 MMA 指令拼成；在 Warp specialization 中，Warp 也可能主要承担加载或写回 |
| Instruction Tile | 一条 MMA 指令描述的 \((M_i,N_i,K_i)\) 运算 | 是指令级计算形状，受数据类型和指令变体约束 |

以传统 Warp MMA 为例，假设：

- CTA Tile 为 \(128\times128\times32\)；
- 4 个 Warp 按 \(2\times2\) 排列，每个负责 \(64\times64\) 输出；
- 指令形状为 `m16n8k16`。

那么每个 Warp 在一个 \(K=32\) 阶段需要：

\[
(64/16)\times(64/8)\times(32/16)=64
\]

条 Warp 级 MMA 指令。所有 K 阶段继续累加到同一输出 Tile。

这里有两个边界：

- **K Tile 通常表示归约循环的一段**；只有采用 Split-K 等方案，才把同一输出块的 K 工作分给多个 CTA。
- **SM100 的 2-CTA MMA 会跨两个 CTA 协作**，不能直接套用“一个 CTA 的所有 Warp 分割自己的 accumulator”这一传统模型。Persistent kernel 中，一个 CTA 还可能依次处理多个工作 Tile。[CUTLASS：Efficient GEMM](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/efficient_gemm.html)、[SM100 GEMM 支持说明](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/blackwell_functionality.html)

**Q28｜P0：一个 CTA 内的 Thread/Warp 如何分工加载 A/B 与执行 MMA？**

要区分“搬运数据的线程划分”和“执行 MMA 的线程划分”。**同一线程加载的数据，不一定就是它在 MMA 中持有的数据。**

传统 `mma.sync` 路径一般是：

```text
线程协作加载 A/B → SMEM
                         ↓
Warp 按指令要求加载寄存器 fragment
                         ↓
32 个线程共同执行 mma.sync
                         ↓
各线程持有自己的 accumulator fragment
```

加载阶段通常让相邻线程访问相邻 GMEM 地址，以形成合并访问；计算阶段则按照 MMA 规定的 lane-to-fragment 映射分配元素。二者通过 SMEM 布局和加载指令衔接。

SM100 的典型 Warp-specialized 路径则按角色组织：

| 角色 | 典型任务 |
|---|---|
| Producer / Load | 发起 TMA，把下一阶段 A/B 搬到 SMEM |
| MMA | 等待输入就绪，由选出的一个线程发起 `tcgen05.mma` |
| Epilogue | 等待结果就绪，将 TMEM accumulator 读入寄存器，执行缩放、融合操作和写回 |
| Scheduler（部分内核） | 获取并分配后续工作 Tile |

这些是逻辑角色，具体 Warp 数量、是否合并角色，由 kernel schedule 决定。TMA 中线程主要负责发起搬运，实际数据传输由硬件完成。

**`tcgen05.mma` 的单线程发起语义只适用于这类指令，不能推广到整个 `tcgen05` 家族。** 例如 TMEM 的 `tcgen05.ld/st` 仍有各自的 Warp 协作要求。[CUTLASS：tcgen05 编程指南](https://docs.nvidia.com/cutlass/4.8.0/media/docs/pythonDSL/guides/mma/tcgen05_programming.html)、[PTX：Issue Granularity](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#tcgen05-issue-granularity)

**Q29｜P0：GMEM、SMEM、Register、TMEM 分别保存什么数据？**

| 存储位置 | GEMM 中的典型内容 | 作用 |
|---|---|---|
| GMEM | 完整 A/B/C/D，以及 scale、bias 等辅助张量 | 保存输入和最终输出 |
| SMEM | A/B 的阶段 Tile、pipeline barrier、部分 epilogue 暂存 | CTA 内复用数据，衔接异步搬运和计算 |
| Register | 地址、索引、描述符、控制状态、传统 MMA fragment、epilogue 临时值 | 线程直接操作的数据 |
| TMEM | SM100 `tcgen05` 的 accumulator；某些变体还存 A 或 scale 等 | Tensor Core 使用的专用存储 |

SM100 常见的 A/B 均来自 SMEM 的路径可以表示为：

```text
A/B：GMEM ──TMA──> SMEM ──tcgen05.mma──> TMEM accumulator
                                             │
                                         tcgen05.ld
                                             ↓
                                          Register
                                             │
                                          Epilogue
                                             ↓
                                            GMEM
```

Epilogue 也可能先经 SMEM 暂存，再用 TMA 写回。

需要注意：**TMEM 不是普通寄存器数组，也不是普通 Shared Memory**，有独立的分配、布局和访问指令。SM100 这条路径的 accumulator 在 TMEM，因此不能默认每个计算线程都持有一组普通寄存器 accumulator。原始 C 通常在 epilogue 中参与 \(\alpha Acc+\beta C\)，不必预先成为 MMA 的输入。[CUTLASS：GMEM 到 MMA 的数据流](https://docs.nvidia.com/cutlass/4.8.0/media/docs/pythonDSL/guides/mma/tcgen05_programming.html#global-memory-gmem-to-mma-data-flow-overview)

**Q30｜P1：SM100 的 GEMM 执行模型与指令差异是什么？**

把三种常见路径并列，区别最清楚：

| 对比项 | 传统 Warp MMA 路径 | Hopper WGMMA 路径 | Blackwell SM100 tcgen05 路径 |
|---|---|---|---|
| 代表指令 | `mma.sync` | `wgmma.mma_async` | `tcgen05.mma` |
| MMA 发起方式 | 一个 Warp 的 32 线程集体执行 | 一个 Warpgroup 的 128 线程集体执行 | 一个线程发起完整操作 |
| A 来源 | Register fragment | Register 或 SMEM | SMEM 或 TMEM |
| B 来源 | Register fragment | SMEM | SMEM |
| Accumulator | Register | Register | TMEM |
| 完成机制 | 同步 MMA 的指令依赖 | WGMMA commit/wait group | `tcgen05.commit` 与 mbarrier |
| 跨 CTA MMA | 无此模式 | 无此模式 | 支持适用的 `.cta_group::2` 模式 |

这比较的是相应指令路径，并不表示某代架构只能使用表中一种指令。

对 CUTLASS 移植而言，核心影响有三点：

1. **数据布局要重建。** 从寄存器 fragment 转向 SMEM 描述符和 TMEM 布局。
2. **流水线要重建。** 输入就绪、MMA 完成、SMEM 可覆盖、TMEM 可读，是不同事件。
3. **分工要重建。** 计算发起与结果读取可以交给不同角色；增加 MMA Warp 数不再直接等于增加独立计算 Tile。

另外，**Cluster 的大小与 `.cta_group::2` 是不同概念**：Cluster 可以包含多个 CTA，但某条双 CTA MMA 只涉及规定的 CTA pair。[CUTLASS：Blackwell SM100 GEMM](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/blackwell_functionality.html)

**Q31｜P0：`tcgen05.mma` 的输入输出及同步语义有什么区别？**

数学上可以理解为：

\[
Acc_{\text{TMEM}}\leftarrow AB+Acc_{\text{TMEM}}
\]

基本形式还可以通过控制参数忽略旧 accumulator，开始一次新的累加。概念参数如下；这不是可直接编译的完整 PTX：

```text
tcgen05.mma(
    TMEM accumulator 地址,
    A 的 SMEM 描述符或 TMEM 地址,
    B 的 SMEM 描述符,
    指令描述符,
    是否使用旧 accumulator
)
```

描述符定义硬件如何解释布局、类型和运算形状。**传给指令的是地址和描述符，不是每个 lane 的 A/B 寄存器 fragment。**

同步应分成三件事理解：

| 要保证什么 | 需要关注的机制 |
|---|---|
| A/B 已经准备好，可以开始读 | TMA 完成等待；普通线程写 SMEM 时还涉及 generic/async proxy 可见性 |
| MMA 已完成，可以读取结果或安全复用相关存储 | 发起线程执行普通 `tcgen05.commit`，由对应 mbarrier 跟踪完成 |
| TMEM 读写已完成，可以使用寄存器结果或复用存储 | `tcgen05.wait::ld/st` 等对应机制 |

一个保守的结果读取顺序是：

```text
等待 A/B 阶段就绪
    ↓
选出的发起线程执行 tcgen05.mma
    ↓
同一发起线程执行 tcgen05.commit，关联完成 barrier
    ↓
消费者等待该 barrier 的正确 phase
    ↓
tcgen05.fence::after_thread_sync
    ↓
消费者 Warp 执行 tcgen05.ld
    ↓
tcgen05.wait::ld
    ↓
Epilogue
```

**指令发起后返回，不代表 Tensor Core 已经算完。** 普通 CTA barrier 也不能代替 MMA 完成等待；同样，`tcgen05.wait::ld` 等待的是 TMEM load，并不负责等待 MMA。

输入阶段与输出阶段的 barrier 要分别管理，尤其要防止 Producer 在 MMA 仍读取 SMEM 时覆盖旧阶段。[PTX：tcgen05 同步与完成机制](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#tcgen05-memory-consistency-model)

**Q32｜P1：Shared Memory Swizzle、Bank Conflict、Tensor Core 访问布局之间是什么关系？**

三者分别回答：

- **Bank conflict：** 一次访问为什么发生带宽损失？
- **Swizzle：** 如何重新安排逻辑元素对应的物理地址？
- **Tensor Core 访问布局：** MMA 或加载指令要求怎样解释这些地址？

SMEM 通常有 32 个 bank。对常见的 32-bit word 访问，可用下面的简化模型分析：

\[
bank=(byte\_address/4)\bmod32
\]

同一事务中，多个不同地址争用同一个 bank，可能导致拆分或串行处理；读取同一位置的广播不能简单算作这种冲突。

例如，32 个线程分别读取一个 row-major `float X[32][32]` 的 `X[lane][0]`：

\[
bank=(32\times lane)\bmod32=0
\]

所有线程都命中 bank 0。普通 CUDA 转置中，可以通过 padding 改为 `X[32][33]` 分散访问。

Swizzle 则通过地址位重排，常见方式包含 XOR，让原本冲突的访问落到不同 bank。**它改变物理存储位置，保持逻辑矩阵元素的含义。** TMA 可以在 GMEM→SMEM 时按指定模式执行这种重排。[CUDA：Shared-Memory Bank Swizzling](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html#shared-memory-bank-swizzling)

对 Tensor Core 路径，还必须保证三方一致：

```text
写入端采用的布局
        =
SMEM 中实际的数据布局
        =
MMA 描述符或加载指令解释的布局
```

因此，不能看到冲突就任意 padding，也不能认为所有 Tile 都应该使用同一种 swizzle。应先根据数据类型、major mode、指令形状和对齐要求选择合法布局，再检查访问效率。**布局合法关系到正确性；在合法布局中减少冲突，才是性能优化。**
